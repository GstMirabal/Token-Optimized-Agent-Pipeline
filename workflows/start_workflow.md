# 🛡️ Workflow: Start (Pipeline Initiation)

Master entry protocol optimized to minimize token consumption and strictly invoke the execution pipeline.

## Execution Flow

| Phase | Step | Action / Constraint |
| :--- | :--- | :--- |
| **0. Zero-Memory Initialization** | `read_anchor` | Subagents MUST initialize with **Zero-Memory**. The absolute first operation is to extract the topology map from `docs/active_state.json` (if it doesn't exist yet, see `first_run_scaffold` below). **Mirror reconciliation**: if `.agent_state/mirror.json` disagrees with the anchor, this is NOT a collision — the anchor wins (the mirror is the backup; staleness only means a previous session ended without the Stop hook firing). Resync it (`python3 .agents/hooks/state_mirror.py`) and continue. The mirror is only authoritative when the anchor itself is missing or corrupt (crash recovery). |
| **0. Zero-Memory Initialization** | `read_ruleset` | Immediately after the anchor, read `agents.md` and `docs/0_SYSTEM_OVERVIEW.md` to adopt current governance. |
| **0. Zero-Memory Initialization** | `pip_setup` | Check if `.agents/installed.lock` exists. If not, create virtual environment `.agents/venv_skillopt/`, install the lean core with `.agents/venv_skillopt/bin/pip install -r .agents/requirements-core.txt`, and write `.agents/installed.lock` recording the ISO timestamp and the requirement set installed (so a later reader knows *what* this environment contains). The heavy skillopt stack (`requirements-skillopt.txt`) installs on demand only when that skill first runs. |
| **0. Zero-Memory Initialization** | `read_graph` | Skip graph construction on tiny hosts (fewer than ~25 source files — a targeted grep is cheaper than building and loading a graph). Otherwise, if `graphify-out/graph.json` is missing, build it with `.agents/venv_skillopt/bin/graphify update .`; if present, query it via MCP/CLI to align on boundaries. |
| **0.4 Drift Check** | `drift_check` | Run `python3 .agents/scripts/detect_drift.py`. It compares `last_close_commit` against `HEAD` and **reports a verdict, not a boolean** — a non-empty range is not drift by itself, because `deployment_workflow.md` Phase 4 seals `[Unreleased]` into a released section and tags it without touching `last_close_commit`, so recorded commits keep landing after the last close. The range is split against **sealing tags** (tags whose version owns a `## [X.Y.Z]` section) and the exit code follows the action required: **`S`** every commit covered → `0`, reports and proposes refreshing the baseline; **`M`** partially covered → `2`, lists only the uncovered; **`U`** none covered and `[Unreleased]` empty → `2`; **`A`** uncovered commits with `[Unreleased]` non-empty → `2`, they may be recorded there but reachability cannot prove it per commit; **`R`** no tag owns a section → `2`, nothing proves any of them recorded. **On any `2`, run `/agents:reconcile` before Phase 2 handoff**, because new work stacked on a state that misreports the repository multiplies the inconsistency instead of resolving it. **An orphaned baseline degrades, it does not lie**: `close_workflow.md` Phase 4 records HEAD on the sprint branch and deployment squash-merges it, so the recorded commit stops being an ancestor of the base branch — the check falls back to their merge-base and says so, because `git cat-file -e` cannot detect this (the orphaned object still exists). Reachability proves the **range** is covered, never that each commit has its own entry: PRs `#26`-`#30` were ancestors of a tag and still unrecorded, and the `S` report states this. Rationale: `docs/decisions/ADR-0002-drift-verdict-exit-codes.md`. **This runs BEFORE `state_claim`, never after**: claiming the lock sets `status: IN_PROGRESS`, and a check keyed on the previous status would be reading its own side effect. Without a baseline recorded yet it says so and passes, rather than staying silent — silence is what let five merged pull requests go unrecorded for a week. |
| **0.5 State Claim** | `state_claim` | **Write the anchor. This workflow used to write nothing at all** — all nine of its steps read or verified, so `session_id` was always the *last closed* session's, never the running one. Run `python3 .agents/scripts/session_state.py claim --session-id <this session's UID>` (nucleus: `python3 scripts/session_state.py …`). It sets `status: IN_PROGRESS`, records the UID and `start_time`, and refreshes the mirror. Claiming the lock and recording the session are the same act, so they are one command and not two steps rewriting one file. Exits `2` when another session holds the lock; `--takeover` seizes a lock left by a crashed session, and is deliberately manual because a live concurrent session and a dead one look identical from here. |
| **0.6 Readiness Probe** | `readiness_probe` | Run `python3 .agents/scripts/session_probe.py`. **Advisory: it proposes and never executes.** Reports a stale knowledge graph, absent documentation artifacts (`docs/decisions/`, Blueprints), and — see `platform_probe` — platform controls. Proposing `/agents:revdoc` is as far as it goes: that protocol reads all of `docs/` and rewrites contracts in place, which `agents.md §2 triple_lock` reserves for human authorization. A gap the human has seen and accepted is recorded in `acknowledged_gaps` in the anchor, so the proposal stops repeating. |
| **0.7 Platform Probe** | `platform_probe` | Part of the same script. Checks secret scanning, push protection, Dependabot updates and alerts, branch protection, repository metadata and the community files, and proposes `/agents:harden`. **Cached for 7 days** (`last_platform_probe`): repository configuration changes a couple of times a year, and a check that fires every session is a check that gets ignored. **Skipped silently** when `gh` is absent or the remote is not GitHub. Community files are checked **against the tree, never against `community/profile`** — that endpoint reports `issue_template` as `null` whenever templates live in a directory, which is the current form, and this repository ships three while scoring `null` at 100% health. |
| **1. Collision Guard** | `session_lock_check` | Abort if `status` in `docs/active_state.json` is `IN_PROGRESS` under a different session UID (crash forensics). **The check is now armed**: `state_claim` above is what writes that state — before Phase 019 nothing anywhere did, so this guard could never fire. **Nucleus mode** (`.git` is a real repo directory, not a submodule pointer — same check the installer uses): only Phase 1.5 (bridge/scaffold) is PROHIBITED (`nucleus_neutrality`); Phase 0 and `lightweight_sync` still run, with `.agents/`-prefixed paths resolving to the repo root (e.g. `./venv_skillopt/`). |
| **1. Collision Guard** | `lightweight_sync` | Perform a lightweight git check (`git fetch --tags` & `git status`) on both project and submodule. If a **newer `.agents` tag** exists than the one pinned (`git -C .agents describe --tags` vs `git -C .agents tag --sort=-v:refname \| head -1`), **report it to the human with a pointer to `.agents/CHANGELOG.md` and await explicit authorization** — auto-updating the governance submodule is PROHIBITED (same supply-chain doctrine as RA-10). *Nucleus mode: `git describe` naturally runs ahead of the latest tag on `main` — commit offset alone is NOT drift.* **New-rule notice** (covers the host that's already onboarded and only meets a rule addition at a later pin-bump — `standardization_workflow.md` Phase 6's Onboarding Scenario Matrix is explicitly "first pipeline session only" and never re-fires for this case): once the human authorizes the bump, diff `agents.md §0`'s Rule Contexts index between the old and new pinned commit; if a rule file is newly present, surface a one-time notice naming it. Advisory only — nothing blocks — but the human stops depending on noticing "a version exists" without knowing what it actually adds. |
| **1.5 Bridge Provision** | `bridge_check` | Run `.agents/scripts/install_claude.sh` if `.agents/.claude_bridge.lock` is missing, its recorded commit differs from `git -C .agents rev-parse HEAD` (i.e. the submodule was deliberately updated since the last install — new agents/commands/skills need linking), **or** the linked artifacts themselves are gone from `.claude/` despite a matching lock (a `git clean -fd`/manual deletion wipes the host's untracked bridge without touching the lock, which lives inside the submodule). The installer is idempotent; `hooks/on_init.py` performs this same check (`sync_commands` + `bridge_intact` sentinel) automatically at session start. |
| **1.5 Bridge Provision** | `first_run_scaffold` | If `docs/active_state.json` is missing, this is the first pipeline session in this host: load the **Onboarding Scenario Matrix** (`standardization_workflow.md` Phase 6) and route the detected scenario (greenfield / prior agents / mature) **before** Phase 2 handoff. The matrix lives there — not here — because first-run routing is a one-time cost while this workflow loads on EVERY session (`rules/token_economy.md §3`). |
| **2. Pipeline Handoff** | `pipeline_invocation` | Explicitly hand command to the **Principal Agent** to initiate Phase 1 (Planning) of the Core Workflow. |
| **2. Pipeline Handoff** | `delegation_conflict` | If the executing agent **cannot** delegate to subagents — a host session policy forbidding it, a non-interactive runner, an unavailable role — it MUST report that conflict to the human **here**, before Phase 1, and await a decision. Substituting itself for the pipeline silently is PROHIBITED. Precedent: an agent whose session configuration forbade spawning subagents resolved the conflict in favour of that configuration without saying so, and executed a whole sprint alone; Phases 4 and 7 never ran, and nothing detected it for twelve commits because no gate checks whether a phase *happened*. Both gates, once finally run, rejected the branch over defects of exactly the class the sprint had been created to remove. The conflict is legitimate and may well be resolved the same way — what is not legitimate is resolving it without the human knowing it existed. |
